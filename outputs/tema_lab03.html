2. Instrumentul nou: estimate_building_power

Instrument de citire care întoarce puterea totală a dispozitivelor pornite, în W, și lista lor. Logica este în building.py, iar instrumentul în server.py.

Logica, în building.py

Am adăugat o metodă nouă în secțiunea de citire a clasei Building. Modulul rămâne fără nicio dependență de MCP:

    def state(self) -> dict:
        return {"pornite": sorted(self.pornite), "termostat_c": self.termostat_c}

    def power_w(self) -> dict:        dispozitive = [{"nume": n, "putere_w": DEVICES[n]["putere_w"]} for n in sorted(self.pornite)]        return {"putere_totala_w": sum(d["putere_w"] for d in dispozitive), "dispozitive": dispozitive}

Testul rapid din __main__ (python building.py) apelează și metoda nouă:

    print(b.state())
    b.set_device("lampa_led", True)    print(b.power_w())

Instrumentul, în server.py

Două modele Pydantic pentru ieșire, lângă celelalte scheme:

class DevicePower(BaseModel):    nume: str    putere_w: int = Field(description="Puterea nominală, în wați.")
class BuildingPower(BaseModel):    putere_totala_w: int = Field(description="Suma puterilor dispozitivelor pornite, în wați.")    dispozitive: list[DevicePower] = Field(description="Dispozitivele pornite, în ordine alfabetică.")

Instrumentul, adăugat la instrumentele de citire, după get_building_state:

@mcp.tool(annotations=CITIRE)def estimate_building_power() -> BuildingPower:    """Returnează puterea totală (W) a dispozitivelor pornite și lista lor, cu puterea fiecăruia."""    return BuildingPower(**cladire.power_w())
  • annotations=CITIRE (readOnlyHint: true) arată clientului că instrumentul nu modifică starea clădirii.
  • Instrumentul nu are argumente, deci nu poate primi date greșite. Din același motiv nu are nevoie de _domeniu: power_w nu ridică BuildingError.
  • Tipul de retur este un model Pydantic, deci FastMCP generează outputSchema și completează automat structuredContent. Modelul imbricat DevicePower apare ca schemă de obiect în items.

  • inputSchema este gol și are additionalProperties: false, deci orice argument trimis în plus e respins.

3. Cererea și răspunsul complete (raw_client.py)

Server pornit pe HTTP. Am pornit trei dispozitive, ca rezultatul să fie interesant, apoi am apelat instrumentul nou.

Comenzile

python server.py http                                     # în alt terminal
python raw_client.py call set_device_state name=radiator on=true
python raw_client.py call set_device_state name=lampa_led on=true
python raw_client.py call set_device_state name=ventilatie on=true
python raw_client.py call estimate_building_power

Portul 8000 era ocupat de o altă instanță a serverului, pornită cu codul vechi. De aceea serverul actualizat a rulat pe portul 8001, iar raw_client.py a fost îndreptat spre aceeași adresă. Mesajele JSON-RPC și antetele MCP nu depind de port.

4. Paragraful despre handle-uri

Ce instrumente ar avea un server de clădire cu scenario_id, cât ar trăi un scenariu și ce s-ar întâmpla la un identificator expirat.

Un server de clădire cu handle-uri ar avea un instrument de creare, create_scenario(copiaza_starea_reala=False), care întoarce un scenario_id opac și greu de ghicit (de exemplu scn_ + un UUID) și momentul expirării. Instrumentele existente ar primi scenario_id ca prim argument: set_device_state, set_thermostat, get_building_state, reset_building, estimate_building_power. Ar mai exista list_scenarios și delete_scenario pentru eliberarea explicită. Instrumentele fără stare (get_device_info, check_conflict, estimate_energy) nu au nevoie de handle. Un scenariu ar trăi printr-un TTL glisant, de exemplu 30 de minute de la ultima folosire, cu o limită maximă (24 de ore) și un număr maxim de scenarii per client, ca memoria să nu crească nelimitat. Scenariile s-ar păstra într-o stocare comună (Redis cu expirare), pentru ca orice instanță a serverului să poată răspunde. La un identificator expirat sau necunoscut, instrumentul ar întoarce o eroare de execuție (isError: true) cu un mesaj explicit, de exemplu „Scenariul scn_… a expirat sau nu există. Creați altul cu create_scenario.” Modelul ar putea astfel să se corecteze singur. Serverul nu ar recrea niciodată scenariul în tăcere și nu ar folosi starea reală în locul lui, pentru că acțiunile s-ar aplica unei alte clădiri decât cea pe care o crede clientul.

Codul este în building.py (metoda power_w) și server.py (modelele DevicePower, BuildingPower și instrumentul estimate_building_power). Toate ieșirile de mai sus provin din rulări reale.
