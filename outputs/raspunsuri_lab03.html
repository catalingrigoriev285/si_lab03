3.4. Exerciții (A) — scheme de date și erori

Server pornit cu python server.py (stdio, în Inspector) și python server.py http (pentru apelurile cu raw_client.py).

A1 Schema de intrare

Cum arată câmpurile name și hours în formular? Găsiți în schemă enum, exclusiveMinimum și maximum.

  • name apare în formular ca listă derulantă (select) cu cele 5 valori permise. Nu se poate scrie un nume liber, pentru că tipul Literal[...] din Python devine enum în schema JSON.
  • hours apare ca câmp numeric, cu descrierea „Durata de funcționare, în ore (0-24].” Limitele vin din Field(gt=0, le=24): gt devine exclusiveMinimum, iar le devine maximum.

inputSchema pentru estimate_energy (din tools/list)

{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "name": {
      "enum": ["lampa_led", "radiator", "aer_conditionat", "jaluzele", "ventilatie"],
      "type": "string"
    },
    "hours": {
      "description": "Durata de funcționare, în ore (0-24].",
      "exclusiveMinimum": 0,
      "maximum": 24,
      "type": "number"
    }
  },
  "required": ["name", "hours"]
}

get_device_info are același enum pentru name. Ambele câmpuri sunt în required, iar additionalProperties: false respinge argumentele în plus. Prin comparație, set_thermostat folosește ge/le, deci limitele sunt inclusive: minimum: 10, maximum: 30.

A2 Schema de ieșire

Apelați get_device_info cu radiator. Comparați content cu structuredContent. De ce le trimite serverul pe amândouă?

"result": {
  "content": [
    { "type": "text",
      "text": "{\"nume\":\"radiator\",\"categorie\":\"încălzire\",\"putere_w\":1500,\"note\":\"Controlat de termostatul camerei.\"}" }
  ],
  "structuredContent": {
    "nume": "radiator",
    "categorie": "încălzire",
    "putere_w": 1500,
    "note": "Controlat de termostatul camerei."
  },
  "isError": false,
  "resultType": "complete"
}
  • content este o listă de blocuri pentru afișare. Aici e un singur bloc text, care conține obiectul serializat ca șir de caractere (JSON cu ghilimele escapate).
  • structuredContent conține același obiect, dar ca JSON propriu-zis, conform cu outputSchema generată din modelul Pydantic DeviceInfo. Câmpurile sunt tipizate (putere_w e număr întreg).

De ce amândouă: pentru compatibilitate. Specificația spune că, dacă un instrument are outputSchema, serverul trebuie să pună în structuredContent date conforme, iar clientul ar trebui să le valideze. Tot specificația cere ca serverul să pună același JSON și ca text în content. Clienții mai vechi și modelele care citesc doar text folosesc content. Codul care prelucrează datele (validare, afișare în tabele, calcule) folosește structuredContent, fără să mai parseze text. FastMCP generează automat ambele câmpuri.

A3 Un rezultat care nu e obiect

list_devices întoarce o listă. Ce a făcut FastMCP cu lista și de ce?

outputSchema

{
  "type": "object",
  "properties": {
    "result": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["result"],
  "x-fastmcp-wrap-result": true
}

Rezultatul apelului

"content": [{ "type": "text",
  "text": "[\"aer_conditionat\",\"jaluzele\",
            \"lampa_led\",\"radiator\",\"ventilatie\"]" }],
"structuredContent": {
  "result": ["aer_conditionat", "jaluzele",
             "lampa_led", "radiator", "ventilatie"]
},
"_meta": { "fastmcp": { "wrap_result": true } }

FastMCP a împachetat lista într-un obiect cu o singură cheie, result. Schema de ieșire e de tip object, nu array, și e marcată cu x-fastmcp-wrap-result: true. Răspunsul are și _meta.fastmcp.wrap_result: true.

De ce: MCP cere ca structuredContent să fie un obiect JSON, iar outputSchema să descrie un obiect ("type": "object"). O listă, un șir sau un număr returnat direct nu ar fi valid. Marcajul îi permite clientului FastMCP să despacheteze automat valoarea (result.data devine din nou lista). În content, textul conține lista neîmpachetată.

A4 Două erori de execuție

get_device_info cu name=frigider, apoi estimate_energy cu name=radiator și hours=30. Cine a produs mesajul: codul vostru sau validarea schemei? Ce valoare are isError?

ApelMesaj primit (în content[0].text)isError
get_device_info
name=frigider		 1 validation error for call[get_device_info] name — Input should be 'lampa_led', 'radiator', 'aer_conditionat', 'jaluzele' or 'ventilatie' [type=literal_error, input_value='frigider'] true
estimate_energy

  • Ambele mesaje sunt produse de validarea schemei (Pydantic, prin FastMCP), nu de codul nostru. Se vede din formatul validation error … [type=literal_error] / [type=less_than_equal]. Funcțiile get_device_info și estimate_energy nici nu au rulat. Mesajul nostru din building.py („Dispozitiv necunoscut: frigider. Cunoscute: …”) nu apare, pentru că enum respinge numele înainte de apel.
  • isError este true în ambele cazuri. Sunt erori de execuție, nu de protocol. Răspunsul are result (nu error), iar HTTP întoarce 200. De aceea CLI-ul se încheie cu un cod de ieșire nenul, deși comanda în sine a funcționat.
  • Verificarea din Building._check rămâne o a doua linie de apărare, utilă când biblioteca e folosită direct, fără MCP.

A5 O eroare de domeniu

set_device_state cu radiator, on=true, apoi cu aer_conditionat, on=true. Ce mesaj primiți? Unde a fost scris?

1. radiator, on=true isError: false

"structuredContent": {
  "pornite": ["radiator"],
  "termostat_c": 21.0
}

2. aer_conditionat, on=true isError: true

"content": [{ "type": "text", "text":
  "Nu pornesc aer_conditionat: conflict
   RIDICAT cu radiator, care este pornit.
   Încălzire și răcire simultană,
   consum inutil." }]

Mesajul a fost scris în building.py. Metoda Building.set_device găsește conflictul de nivel RIDICAT și ridică BuildingError cu textul de mai sus. Descrierea „Încălzire și răcire simultană, consum inutil.” vine din dicționarul CONFLICTE. server.py nu scrie niciun mesaj: funcția _domeniu doar prinde BuildingError și o ridică din nou ca ToolError(str(e)), pe care FastMCP o transformă în rezultat cu isError: true. Rezultatul de eroare nu are structuredContent.

Spre deosebire de A4, aici argumentele sunt valide ca formă, dar încalcă o regulă a domeniului. Schema nu poate exprima o astfel de regulă, deoarece ea depinde de starea curentă. Mesajul este clar, așa că modelul îl poate citi și corecta singur cererea (de exemplu, oprește întâi radiatorul).

4.5. Exerciții (B) — transportul HTTP

Server pornit separat cu python server.py http la http://127.0.0.1:8000/mcp.

B1 Un singur server, mai mulți clienți

Porniți ventilatie din Inspector, apoi rulați client_demo.py. Ce observați la prima linie? Unde a dispărut ventilația și cine a oprit-o?

Ana    -> set_device_state: {'pornite': ['radiator', 'ventilatie'], 'termostat_c': 21.0}
Bogdan -> get_building_state: {'pornite': ['radiator', 'ventilatie'], 'termostat_c': 21.0}
Bogdan -> set_device_state: isError = True | Nu pornesc aer_conditionat: conflict RIDICAT cu radiator, care este pornit. Încălzire și răcire simultană, consum inutil.
  • În prima linie, Ana pornește doar radiatorul, dar starea întoarsă conține și ventilatie. Ventilația a fost pornită de alt client (Inspector). Toți clienții lucrează pe același obiect cladire din procesul serverului. Starea aparține serverului, nu conexiunii.
  • După rulare, get_building_state din Inspector întoarce {"pornite": [], "termostat_c": 21.0}, deci ventilația a dispărut. A oprit-o client_demo.py: la final, clientul Anei apelează reset_building („curățenie”), care oprește toate dispozitivele, inclusiv ventilația pornită din Inspector. Un client a anulat, fără să știe, acțiunea altui client.

B2 Repornirea

Opriți și reporniți serverul. Ce s-a întâmplat cu starea? Ce ar trebui schimbat ca starea să supraviețuiască repornirii?

Înainte de oprire am pornit lampa_led. După repornire, get_building_state întoarce {"pornite": [], "termostat_c": 21.0}. Starea s-a pierdut și a revenit la valorile implicite. Ea exista doar în memoria procesului (cladire = Building() se creează din nou la fiecare pornire).

Ce trebuie schimbat: starea trebuie persistată în afara procesului:

  • Varianta simplă: un fișier JSON sau o bază SQLite. Building încarcă starea la pornire (în __init__) și o salvează după fiecare modificare (set_device, set_thermostat, reset). Scrierea trebuie să fie atomică: se scrie un fișier temporar, apoi se redenumește.
  • Pentru mai multe instanțe de server în spatele unui echilibrator de încărcare: o stocare comună (PostgreSQL, Redis), cu tranzacții sau blocări. Altfel, două cereri simultane pot porni radiatorul și aerul condiționat, ocolind verificarea de conflict.

Modificarea se face în building.py, care deține starea. server.py rămâne neschimbat.

B3 Agentul opțional, model real

După modificarea din 4.4, cereți agentului „Pornește radiatorul”. Verificați în Inspector cu get_building_state.

Modificarea în agent.py (linia 93):

self.mcp = Client(SERVER)                        # înainte: stdio, proces copil
self.mcp = Client("http://127.0.0.1:8000/mcp")   # acum: serverul HTTP partajat

La cererea „Pornește radiatorul”, agentul ar trebui să aleagă set_device_state cu {"name": "radiator", "on": true}. Schema îi oferă valorile exacte în enum, deci nu trebuie să ghicească numele. Apoi, get_building_state din Inspector ar trebui să întoarcă {"pornite": ["radiator"], "termostat_c": 21.0}. Efectul ar trebui să se vadă imediat, pentru că agentul și Inspector sunt doi clienți ai aceluiași proces server, la fel ca în B1.

Exercițiul cere un model real (de exemplu Gemini) și nu a fost rulat aici. Mai sus este descris rezultatul așteptat, dedus din comportamentul observat în B1.

B4 Discuție: starea partajată

Un exemplu în care starea partajată este dorită, unul în care este o problemă. Cum ar arăta instrumentul care creează un handle?

  • Dorită Clădirea reală are o singură stare fizică. Administratorul (din panou), aplicația mobilă a unui locatar și agentul AI trebuie să vadă aceeași realitate. Dacă cineva a pornit radiatorul, agentul trebuie să știe asta ca să nu pornească aerul condiționat. Regula de conflict funcționează doar pentru că starea e comună (vezi mesajul lui Bogdan din B1).
  • Problemă Mai mulți studenți sau teste automate folosesc același server de laborator. Unul rulează reset_building și distruge experimentul altuia (exact ce s-a întâmplat cu ventilația în B1). Similar, un agent care face o simulare „ce-ar fi dacă” nu ar trebui să modifice starea reală a clădirii.

Instrumentul care creează un handle: serverul ține un dicționar scenario_id → Building, iar fiecare instrument primește identificatorul ca argument obișnuit:

class ScenarioCreated(BaseModel):
    scenario_id: str = Field(description="Identificatorul de transmis la apelurile următoare.")
    expira_la: str   = Field(description="Momentul expirării (ISO 8601, UTC).")

@mcp.tool(annotations=MODIFICARE)
def create_scenario(copiaza_starea_reala: bool = False) -> ScenarioCreated:
    """Creează o clădire simulată, separată de celelalte, și întoarce identificatorul ei."""
    ...

@mcp.tool(annotations=MODIFICARE)
def set_device_state(scenario_id: str, name: DeviceName, on: bool) -> BuildingState: ...

@mcp.tool(annotations=CITIRE)
def get_building_state(scenario_id: str) -> BuildingState: ...

@mcp.tool(annotations=DISTRUGERE)
def delete_scenario(scenario_id: str) -> None: ...

Exemplu de răspuns: {"scenario_id": "scn_7f3a9c", "expira_la": "2026-10-29T20:00:00Z"}. Fiecare client lucrează în propriul scenariu, iar starea nu depinde de conexiune. Dacă scenariile sunt păstrate într-o stocare comună (de exemplu Redis), orice instanță a serverului poate răspunde la orice cerere.

C1 Antetele

fara-antet și antet-gresit. Ce verifică serverul? De ce contează potrivirea antet-corp, dacă serverul citește oricum corpul?

HTTP 400
{ "jsonrpc": "2.0", "id": 1,
  "error": { "code": -32020,
             "message": "mcp-name header does not match the request body's 'name' parameter" } }

Ce verifică: antetele Mcp-Method și (pentru tools/call) Mcp-Name trebuie să existe și să aibă aceleași valori ca method și params.name din corp. Lipsa antetului (fara-antet) și o valoare diferită (antet-gresit: antet reset_building, corp get_device_info) produc același refuz, cu eroare de protocol -32020, înainte de rularea instrumentului.

De ce contează: antetele nu sunt citite de server, ci de intermediari: echilibratorul de încărcare, gateway-ul API, firewall-ul, limitatorul de rată, jurnalele. Aceștia decid pe baza antetelor, fără să parseze JSON-ul. De exemplu, un firewall permite instrumentele de citire și blochează reset_building. Dacă serverul ar accepta nepotriviri, un atacator ar trimite antetul Mcp-Name: get_device_info (permis) cu corpul reset_building. Firewall-ul ar lăsa cererea să treacă, iar serverul ar executa resetarea. Verificarea antet-corp garantează că se execută exact ce a aprobat intermediarul.

C2 Versiunea

Ce informație din răspuns i-ar permite unui client să reîncerce corect?

HTTP 400
{ "jsonrpc": "2.0", "id": 1,
  "error": { "code": -32022,
             "message": "Unsupported protocol version",
             "data": { "supported": ["2026-07-28"], "requested": "2030-01-01" } } }

Câmpul error.data.supported conține lista versiunilor acceptate de server. Clientul alege din ea cea mai nouă versiune pe care o cunoaște și el (aici 2026-07-28) și retrimite cererea, cu acea versiune în antetul MCP-Protocol-Version și în params._meta. data.requested confirmă ce valoare a primit serverul. Aceeași listă se poate obține și dinainte, din server/discover (supportedVersions).

C3 Metoda

python raw_client.py metoda. Eroare de protocol sau de execuție?

HTTP 404
{ "jsonrpc": "2.0", "id": 1,
  "error": { "code": -32601, "message": "Method not found", "data": "tools/run" } }

Eroare de protocol. Răspunsul are câmpul error (nu result), cu codul JSON-RPC standard -32601 Method not found, iar HTTP întoarce 404. Metoda tools/run nu există, metoda corectă fiind tools/call. Greșeala aparține programatorului clientului. Modelul nu o poate corecta, pentru că nu alege metodele JSON-RPC.

C4 Instrumentul inexistent

Specificația dă „instrument necunoscut” ca exemplu de eroare de protocol (-32602). Ce întoarce FastMCP? Un argument pentru fiecare variantă, din punctul de vedere al unui agent cu LLM.

HTTP 200
{ "jsonrpc": "2.0", "id": 1,
  "result": { "content": [{ "type": "text", "text": "Unknown tool: 'porneste_tot'" }],
              "isError": true,
              "resultType": "complete" } }

FastMCP nu respectă exemplul din specificație. Întoarce o eroare de execuție (result cu isError: true, HTTP 200), nu o eroare de protocol cu -32602.

  • Pentru eroare de protocol (-32602, varianta din specificație): lista instrumentelor se poate afla oricând cu tools/list. Un apel către un instrument inexistent înseamnă că gazda are o listă învechită sau o eroare de cod. Eroarea de protocol ajunge la codul gazdei, care o poate trata direct: reîmprospătează tools/list, refuză cererea, scrie în jurnal. Nu consumă un pas al modelului și nu îi expune modelului detalii interne. Intermediarii și sistemele de monitorizare o pot detecta după cod.
  • Pentru eroare de execuție (varianta FastMCP): la un agent, numele inexistent provine de obicei dintr-o halucinație a modelului. Majoritatea buclelor de agent trimit înapoi la model doar rezultatele (content), iar erorile de protocol devin excepții care opresc bucla sau se pierd. Cu isError: true, modelul citește „Unknown tool: 'porneste_tot'” la pasul următor și se poate corecta singur, alegând un instrument real. Aceasta este exact definiția erorii de execuție: o eroare pe care modelul o poate corecta.

7. Temă, punctul 4 — handle-uri

Un paragraf (maximum 15 rânduri) despre un server de clădire cu scenario_id.

Un server de clădire cu handle-uri ar avea un instrument de creare, create_scenario(copiaza_starea_reala=False), care întoarce un scenario_id opac și greu de ghicit (de exemplu scn_ + un UUID) și momentul expirării. Instrumentele existente ar primi scenario_id ca prim argument: set_device_state, set_thermostat, get_building_state, reset_building, estimate_building_power. Ar mai exista list_scenarios și delete_scenario pentru eliberarea explicită. Instrumentele fără stare (get_device_info, check_conflict, estimate_energy) nu au nevoie de handle. Un scenariu ar trăi printr-un TTL glisant, de exemplu 30 de minute de la ultima folosire, cu o limită maximă (24 de ore) și un număr maxim de scenarii per client, ca memoria să nu crească nelimitat. Scenariile s-ar păstra într-o stocare comună (Redis cu expirare), pentru ca orice instanță a serverului să poată răspunde. La un identificator expirat sau necunoscut, instrumentul ar întoarce o eroare de execuție (isError: true) cu un mesaj explicit, de exemplu „Scenariul scn_… a expirat sau nu există. Creați altul cu create_scenario.” Modelul ar putea astfel să se corecteze singur. Serverul nu ar recrea niciodată scenariul în tăcere și nu ar folosi starea reală în locul lui, pentru că acțiunile s-ar aplica unei alte clădiri decât cea pe care o crede clientul.

Rezultatele de la (A), (B1), (B2) și (C) sunt obținute rulând server.py, client_demo.py și raw_client.py din acest proiect (FastMCP 4.1.4).
