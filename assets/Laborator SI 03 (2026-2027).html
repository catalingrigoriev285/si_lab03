Expunerea funcționalităților prin servicii standardizate: serverul MCP, scheme de date, mesaje și transport

1. Concepte

1.1. Serviciul și adaptorul

Până acum, datele și regulile clădirii inteligente erau plasate în același fișier cu instrumentele MCP. În practică, funcționalitatea există deja (o bibliotecă, o bază de date, un API intern), iar serverul MCP este un adaptor: o traduce într-o formă standard pe care orice client MCP o poate descoperi și folosi.

building.py nu importă nimic din MCP și poate fi testat singur.
server.py face trei lucruri: declară schemele, traduce erorile și alege transportul.

1.2. Mesajele

MCP folosește JSON-RPC 2.0. Există trei feluri de mesaje:

Mesaj Are id? Conține Exemplu
cerere da method, params tools/call
răspuns același id ca cererea (lipsește doar dacă cererea nu a putut fi citită) fie result, fie error (cu code și message) rezultatul apelului
notificare nu method, params; nu primește răspuns notifications/progress

Versiunea curentă a specificației 2026, folosește protocolul fără stare:

  • nu mai există negocierea inițială initialize și nici sesiunea de protocol;
  • fiecare cerere își poartă singură, în params._meta, versiunea de protocol, capabilitățile clientului și (recomandat) identitatea clientului;
  • serverul trebuie să răspundă la server/discover, prin care spune ce versiuni și capabilități are; clientul îl poate apela înaintea oricărei alte cereri;
  • fiecare rezultat are câmpul resultType ("complete" pentru un rezultat obișnuit).

Materialele mai vechi (inclusiv multe tutoriale) descriu negocierea initialize / notifications/initialized și antetul Mcp-Session-Id. Ele sunt valabile pentru versiunile până la pre-2026. Serverul din laborator acceptă ambele variante; diferența se poate vedea în Inspector.

1.3. Schemele și erorile

Un instrument este descris prin:

  • inputSchema: o schemă JSON a argumentelor (tipuri, valori permise, limite).
  • outputSchema (opțional): o schemă JSON a rezultatului. Dacă există, serverul trebuie să întoarcă în structuredContent date conforme cu ea, iar clientul ar trebui să le valideze. Pentru compatibilitate, serverul ar trebui să pună același JSON și ca text în content; FastMCP o face automat (MCP - Tools).

Specificația deosebește două feluri de erori:

Fel Unde apare Exemple Cine o poate corecta
eroare de protocol câmpul error al răspunsului JSON-RPC metodă inexistentă, cerere malformată, versiune nesuportată programatorul clientului
eroare de execuție result, cu isError: true argument în afara limitelor, regulă de domeniu încălcată adesea chiar modelul, la următorul apel

1.4. Transportul de date

stdio Streamable HTTP
Cine pornește serverul clientul, ca proces copil serverul rulează independent
Câți clienți unul (cel care l-a pornit) oricâți
Pe unde circulă mesajele intrarea și ieșirea standard câte un POST la o singură adresă, de exemplu /mcp
Răspunsul o linie JSON application/json sau un flux SSE pentru acea cerere
Folosit pentru unelte locale servicii partajate, servere la distanță

Pe HTTP, specificația cere (MCP - Streamable HTTP):

  • Antetele MCP-Protocol-Version, Mcp-Method și, pentru tools/call, resources/read și prompts/get, Mcp-Name. Ele copiază valori din corpul mesajului, ca un echilibrator de încărcare (load balancer) sau un firewall să poată decide fără să citească JSON-ul. Serverul verifică dacă antetele corespund corpului;
  • Validarea antetului Origin, ca o pagină web deschisă în browser să nu poată apela un server local (atacul DNS rebinding);
  • Legarea doar la 127.0.0.1 când serverul rulează local.

3. Partea A: scheme de date și erori

3.1. Logica, fără MCP

Rulați:

python building.py

Studiați building.py. Observați că o regulă încălcată (dispozitiv necunoscut, conflict, temperatură în afara limitelor) ridică o excepție de domeniu, BuildingError. Biblioteca nu știe cine o folosește.

3.2. Ce s-a schimbat în server

Deschideți server.py. Observați diferențele față de versiunea laboratorului anterior.

Valorile permise intră în schemă. Numele dispozitivelor devin o enumerare:

DeviceName = Literal["lampa_led", "radiator", "aer_conditionat", "jaluzele", "ventilatie"]

@mcp.tool(annotations=CITIRE)
def get_device_info(name: DeviceName) -> DeviceInfo:

Serverul refuză să pornească dacă lista nu mai corespunde dispozitivelor din building.py. În inputSchema apare "enum": ["lampa_led", "radiator", ...]. Clientul (și modelul) vede lista înainte de apel, iar un nume greșit este respins înainte ca funcția să ruleze.

Tipul de ieșire devine schemă. Un model Pydantic ca tip de retur produce outputSchema:

class DeviceInfo(BaseModel):
    nume: str
    categorie: str
    putere_w: int = Field(description="Puterea nominală, în wați.")
    note: str

Erorile de domeniu devin erori de execuție. Funcția _domeniu prinde BuildingError și ridică ToolError, pe care FastMCP o transformă într-un rezultat cu isError: true:

def _domeniu(fn, *args):
    try:
        return fn(*args)
    except BuildingError as e:
        raise ToolError(str(e)) from e

3.3. Verificarea în Inspector

npx @modelcontextprotocol/inspector --web --protocol-era modern python server.py

Opțiunea --protocol-era modern cere versiunea 2026 a standardului MCP. Fără ea, Inspector folosește implicit varianta veche, pre-2026, care folosește initialize. Deschideți adresa afișată în terminal și conectați serverul cu comutatorul.

4. Transportul HTTP

4.1. Pornirea serverului pe HTTP

Același server.py, cu un argument:

python server.py http

Serverul ascultă la http://127.0.0.1:8000/mcp și rămâne pornit. Lăsați terminalul deschis și lucrați în altul, cu mediul virtual activat.

Fragmentul care alege transportul:

mcp.run(
    transport="http",
    host="127.0.0.1",             # doar local, nu 0.0.0.0
    port=8000,                    # adresa: http://127.0.0.1:8000/mcp
    host_origin_protection=True,  # verifică Host și Origin (implicit, în FastMCP, este oprită)
    show_banner=False,
)

Atenție. În FastMCP 4, verificarea Host / Origin este oprită implicit, deși specificația o cere obligatoriu. De aceea o pornim explicit. Biblioteca nu garantează singură conformitatea: citiți parametrii și verificați.

4.2. Folosirea Inspectorului pentru analiza URL

npx @modelcontextprotocol/inspector --web --transport http --server-url http://127.0.0.1:8000/mcp --protocol-era modern

Pe cardul inspectorului apare acum Streamable HTTP și MCP 2026-07-28. Serverul nu mai e pornit de Inspector: îl puteți opri și reporni independent.

4.3. Utilizare

Cu serverul pornit, rulați:

python client_demo.py

Ana    -> set_device_state: {'pornite': ['radiator'], 'termostat_c': 21.0}
Bogdan -> get_building_state: {'pornite': ['radiator'], 'termostat_c': 21.0}
Bogdan -> set_device_state: isError = True | Nu pornesc aer_conditionat: conflict RIDICAT cu radiator, care este pornit. Încălzire și răcire simultană, consum inutil.

Persoana A vede radiatorul pornit de Persoana B. Starea stă în procesul serverului (obiectul cladire), nu în conexiune. Pe stdio nu observați asta, pentru că fiecare client își pornește propriul server.

Discuție: starea fără sesiuni. Protocolul nu mai are sesiuni, deci serverul nu poate ține „câte o clădire pentru fiecare client" pe baza conexiunii. Specificația cere ca starea care se întinde pe mai multe cereri să fie referită printr-un identificator explicit, transmis la fiecare cerere (MCP - Overview, Statelessness). Forma recomandată este un handle: un instrument de creare întoarce un identificator (de exemplu scenario_id), iar instrumentele următoare îl primesc ca argument obișnuit. Serverul păstrează starea sub acel identificator (MCP - Tools, Stateful Tools). Avantajul: orice instanță a serverului poate răspunde la orice cerere, deci serverul poate fi multiplicat în spatele unui echilibrator de încărcare.

4.4. Utilziarea agentului din laboratorul anterior (HTTP)

În fisierul agent.py din laboratorul precedent, înlocuiți o singură linie:

5. Trimiterea de mesaje

raw_client.py trimite cereri JSON-RPC cu httpx, fără SDK, și afișează tot: antetele, corpul cererii, codul HTTP și corpul răspunsului. Serverul trebuie să ruleze pe HTTP (secțiunea 4.1).

5.1. Prima cerere: server/discover

python raw_client.py discover

Cererea (antetele și corpul):

MCP-Protocol-Version: 2026-07-28
Mcp-Method: server/discover

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {"name": "raw-client", "version": "1.0"},
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

Răspunsul (prescurtat):

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "smart-building-demo", "version": "3.0"}},
    "supportedVersions": ["2026-07-28"],
    "capabilities": {"tools": {"listChanged": false}, "resources": {"subscribe": false, "listChanged": false}, "prompts": {"listChanged": false}},
    "resultType": "complete"
  }
}

Construcția cererii se află în funcția send din raw_client.py: citiți-o.

5.2. Apelarea instrumentelor

python raw_client.py list
python raw_client.py call estimate_energy name=radiator hours=2

În răspunsul lui tools/call găsiți content, structuredContent, isError și resultType. Comparați cu ce afișa Inspector în Partea A: panoul Protocol arată aceleași mesaje; CLI-ul afișează doar rezultatul, fără unele câmpuri de protocol (de exemplu resultType).
